# MP PROGRESS

## Locked decisions
- Project: MATLAB-Based Public-Key Cryptography and Secure Communication Using Group Theory and Modular Arithmetic (Alliance University micro-project, team of 6)
- Runs on desktop MATLAB. Base MATLAB only unless a packet says otherwise, so it runs on any recent release.
- Demo style: commands and typed prompts in MATLAB, with text output and graphs. No clickable app for now.
- Small numbers for clarity. It is an educational simulation, not real security, and the report says so.
- Code layout: code in src/<module>/, one function per file with the file name equal to the function name; tests in tests/; saved figures in outputs/; report material in docs/.
- Entry commands: setup_project (adds the folders to the path) and main_demo (comes at Point 5). Each point may also have a small demo, for example demo_point1.
- Packet files (.md) are kept in packets/ and committed; zip files in packets/ are not.
- Numbers: prime p = 97 and generator g = 5 (the powers of 5 give every number from 1 to 96). Everything works in the group Z_97* (the numbers 1 to 96 with multiplication mod 97).
- Users: Alice, Bob, Carol, Dave, Frank, Grace (6 users). They are set in define_sets and can be changed there.
- Alphabet: the 95 printable ASCII characters (space to ~). A character with code c is plaintext symbol c - 31, so symbols are 1 to 95. Ciphertext values are 1 to 96. The key set K is 1 to 96.
- Cipher: encryption E_k(m) = k*m mod 97 and decryption D_k(c) = j*c mod 97, where j is the inverse of k mod 97. The functions are built in Point 1 (encrypt_symbols, decrypt_symbols, encrypt_text, decrypt_text, key_inverse). In Point 4 the shared Diffie-Hellman secret becomes the key k. The ciphertext value 96 is in C but is not a plaintext symbol, so decrypt_symbols stops with an error when a result would be 96 (this happens with a wrong key).
- Code style: it must run in desktop MATLAB and also in GNU Octave. Use only simple base functions, single-quoted text, no toolboxes, and plain ASCII characters in .m files. The planner tests in Octave; the real MATLAB run is at the end.
- The owner has no MATLAB on the working laptop. Antigravity skips the MATLAB checks. All real MATLAB runs happen later on the demo laptop.
- Tests: tests/test_<name>.m are functions; each prints PASS or FAIL lines through summarize_checks. run_all_tests runs them all and ends with ALL TESTS PASSED.
- Graph: the network is a simple undirected graph (no loops, no repeated edges), built from the relation R1 by define_graph. Vertex i is user i. Each edge is stored once as [i j] with i < j, in increasing order, so edge numbers e1 to e6 stay fixed. Graph code lives in src/graph_network/ (demo: demo_point2).
- Graph analysis: every analysis function takes the adjacency matrix A (true and false, symmetric) and works with vertex numbers 1 to n. The distance between two users is the number of channels on a shortest path, and it is Inf when there is no path (the tables print - for it). Breadth-first search visits the neighbors of a vertex in increasing order, so the shortest path shown is always the same one (the first one found). A bridge channel (bridge_channels) or a cut user (cut_users) is one whose removal splits a connected group into more groups. The number of independent cycles is channels - users + groups (cycle_rank). Removing a channel or a user returns a new matrix and never changes the old one (remove_channel, remove_user).
- Test helper: tests/raises_error.m returns true when a function handle stops with an error; the tests use it to check that bad input is refused.
- Pictures: the network is drawn with base plot commands only (line, fill, text; no graph or digraph, no toolbox). graph_layout gives the places of the users: each connected group is drawn in layers (x = 2.4 times the distance from the smallest user of the group, found with breadth-first search), the users of one layer are 1.6 apart in increasing order from the top, several groups are stacked 1.8 apart, and the drawing is centered on y = 0. The places are always the same for the same network. The 5 pictures are the network, the shortest path from the first to the last user, a shortest cycle, the weak points (bridge channels red, cut users orange) and the network after the first bridge channel is removed (one color for each group). Each picture is saved as a PNG file in outputs/ (point2_network, point2_shortest_path, point2_cycle, point2_weak_points, point2_split). PNG files in outputs/ are not committed (outputs/*.png is in .gitignore).
- Tests never write into outputs/: the tests and the demo run with demo_point2(tempname(), 'off'), which saves into a temporary folder and keeps no figure open.
- Modular arithmetic (Point 3): the code lives in src/group_theory/ (demo: demo_point3). mod_pow(b, e, m) is fast modular exponentiation by repeated squaring: for each bit of e from the left, square the value, and multiply by b when the bit is 1. It needs m to be a whole number from 2 to 2^26 so every product stays below 2^52 and the double numbers are exact; b^0 is 1 (also 0^0). euclid_gcd(a, b) is Euclid's algorithm and gives the steps [a b q r] (a = q*b + r). ext_gcd(a, b) is the extended Euclid algorithm (iterative) and gives g, x, y with a*x + b*y = g; x and y can be negative. mod_inverse(a, m) uses ext_gcd, reduces a mod m first, gives j from 1 to m-1, and stops with an error when gcd(a, m) is not 1. All inputs are checked with is_whole_number (one real finite whole number, at most 2^53 in size); bad input stops with an error. key_inverse (the search from Point 1) stays as it is; mod_inverse gives the same answers, and a check in show_modular compares them for all 96 keys.
- Group Z_p* (Point 3): the group is the numbers 1 to p-1 with multiplication mod p, with p prime (p = 97 by default, from define_sets). group_table(p) gives its multiplication table (p from 2 to 300). check_group(T) checks the group rules for any square table whose elements are called 1 to n: closure (every entry is a whole number from 1 to n), identity, inverses, associativity (all triples) and commutativity; if the table is not closed the other results are false (identity 0, inverses 0). The order of a number is the smallest k with a^k = 1 (mod p); element_order finds it by starting at p-1 and dividing out each prime factor q of p-1 while a^(k/q) is still 1. is_generator tests that a^((p-1)/q) is not 1 for every prime factor q of p-1; the tests compare the two methods, and also compare both with the plain method of multiplying until 1. Limits: is_prime_number and prime_factors up to 2^32, element_order and is_generator up to p = 2^26, find_generators and cyclic_subgroup up to p = 5000, group_table and check_group up to 300. cyclic_subgroup(a, p) gives [a^0, a^1, ..., a^(k-1)] with k the order. Bad input stops with an error.
- Diffie-Hellman (Point 4): the code lives in src/diffie_hellman/ (demo: demo_point4). The public numbers are p = 97 and g = 5. Each user has a secret number from 1 to p-2, set in define_secrets (Alice 6, Bob 15, Carol 23, Dave 41, Frank 58, Grace 77; the owner can change them there). dh_public_value(a, p, g) = g^a mod p. dh_shared_key(a, B, p) = B^a mod p. dh_exchange(a, b, p, g) runs one exchange between two users and gives a struct (public values A and B, both keys, E.agree, E.key, and the check key g^(a*b mod (p-1)) mod p). dh_key_table gives the 6 by 6 table of the keys of all pairs (0 on the diagonal; it is symmetric). check_dh_setup stops with an error when p is not a prime from 5 to 2^26 or g is not a generator of Z_p*, and the functions stop when a secret number is not from 1 to p-2 or a public value is not from 1 to p-1. The shared key is a number from 1 to p-1, so it is a key of the cipher (the key set K). With the default numbers Alice and Bob get the key 85.
- Encryption with the shared key (Point 4): the code lives in src/encryption/ (demo: demo_point4, which now shows the key exchange, the encryption and the eavesdropper one after the other). send_message(txt, i, j, D, S) sends a text from user i to user j: the sender computes the key from the own secret number and the public value of the receiver, the receiver does the same the other way round, the text is encrypted with the key of the sender (encrypt_text) and decrypted with the key of the receiver (decrypt_text). It gives a struct (the names, the public values, both keys, M.agree, the numbers M.cipher, the text M.received and M.ok, which is true when the receiver gets the same text; M.received is empty when the decryption stops with an error, for example when the receiver has a wrong key). The text is one row of at least one of the 95 printable characters. The eavesdropper Eve knows p, g, both public values and the ciphertext. eavesdrop_dh(A, B, p, g) (in src/diffie_hellman/) computes g^1, g^2, ... mod p until it gets A, which gives the secret number a (E.tries is the same as E.secret), and then the key B^a mod p; it needs p up to 1000000 and A from 2 to p-1. try_all_keys(c, S) decrypts a ciphertext with every key of K (p up to 1000): a key stops when a value outside P comes out (for p = 97 the key k stops exactly when the value 97-k is in the ciphertext), and a text is readable when it has only letters, digits, spaces and the characters . , ! ? ' - (69 of the 95 characters). With the default numbers only the key 85 gives a readable text for the demo message. The demo message is 'Meet me at the library at 5 pm, Bob.' from Alice to Bob. The cipher has only 96 keys, so Eve can read the message even without breaking the key exchange; the report says that this cipher is a learning model and is not secure. format_numbers(v, per_row) turns numbers into lines of text for the printouts.
- Secure network (Point 5): the code lives in src/integration/ (demo: demo_point5). define_system(S) gives one struct Y with the sets Y.S, the users, Y.n, the graph Y.G, the secret numbers Y.D, the table of keys Y.K, the adjacency matrix in use Y.A (it starts equal to Y.G.adj; a broken network is Y.A = remove_channel(Y.A, i, j)) and Y.edge_keys, the Diffie-Hellman key of each channel (with the default numbers 85, 12, 42, 90, 32 and 72). check_system(Y) stops with an error when Y is not a proper system. channel_key(Y, i, j) is the key of the channel i-j and is an error for a missing or removed channel. route_message(txt, i, j, Y) sends a text along the shortest path of Y.A, hop by hop: every hop is a send_message with the key of that channel, and every relay decrypts and encrypts again, so the relays can read the text (this is not end-to-end encryption, and the printout says so). An unreachable receiver is not an error: delivered is false and received is empty. show_system(Y) prints the keys of the channels, one message on one channel, one message along a path (Alice to Grace), all 30 pairs and a broken channel, then 7 self-checks; it needs the full connected network. The fixed texts are 'Hello Bob, are you free at 5 pm?' (Alice to Bob), 'Hello Grace, the meeting is at 5 pm.' (Alice to Grace) and 'See you at 5 pm.' (every pair).
- Typed demo (Point 5): main_demo(answers, visible, outdir) in src/integration/ is the entry command of the demo. It prints a menu and asks for every answer with input(prompt, 's'): 1 send a message (sender, receiver and text; the route is shown), 2 key exchange of two users, 3 the channels and their keys, 4 break a channel, 5 repair all channels, 6 the whole report (show_system of the untouched network), 7 the picture of the network with the route of the last message, 0 quit. A user is chosen by number or by name (small or capital letters), and a bad answer asks again. A text is 1 or more of the 95 printable characters. Breaking a channel that does not work says so and goes back to the menu. main_demo(answers) takes a cell array of texts instead of the keyboard (for the tests and for a scripted run) and stops with an error when the answers run out. read_answer (one answer), pick_user (one user) and show_route (prints one route_message result) are its helpers. The run ends with how many messages were sent and how many arrived. test_main_demo checks all this without the keyboard and without writing into outputs/.
- Picture of the route (Point 5): the code lives in src/integration/. route_picture_options(Y, R) gives the colors, widths, styles and title for draw_network (it draws nothing); R is the result of route_message or [] for no route. Broken channels (missing in Y.A) are dotted and gray in every picture. With R = [] or with no route every group of users has its own color (the same 6 shades as picture 5 of Point 2); with a route the channels of the route are thick and green, the sender and the receiver dark green, the users in the middle light green and the others blue. The titles are 'The network now: 6 working channels, 0 broken, 1 group of users', 'No route from Alice to Grace: they are in different groups of users' and 'Alice to Grace: Alice - Bob - Dave - Frank - Grace (4 channels)'. A route that uses a broken channel is an error (route_picture_options:stale). draw_route_picture(ax, Y, R) draws it in the axes ax with the places of graph_layout of the whole network, so the users never move when channels break. show_route_picture(Y, R, visible, outdir) draws it in a figure and saves the PNG file point5_route.png (an older file is replaced; the default folder is outputs/; visible is 'on', the default, to keep the window, or 'off' to close it). main_demo option 7 draws the picture of the route of the last message. The route is forgotten when a channel is broken or repaired (a repair with nothing broken keeps it), so the picture never shows an old route; then it shows the network as it is now. Before a new window opens the old one of main_demo is closed. The tests use visible 'off' and a temporary folder, so no window opens and nothing is written into outputs/. test_route_picture checks all this.

## How we work
1. The project is built in big checkpoints called points. Inside a point the work is cut into small packets (IDs like 1A, 1B, 2A).
2. Before each point, and again before each packet when needed, the planner clones the repo, reads this file and the code, and writes the next packet as a markdown file (packets/PACKET_<ID>_<n>.md, with a files zip when there are files to copy).
3. The owner puts the packet in packets/ and pastes this line into Antigravity: Read packets/PACKET_<ID>_<n>.md and execute it exactly. Decide nothing. If anything fails, stop and tell me.
4. The agent follows AGENTS.md, commits, pushes and reports DONE with the done-checks.
5. The planner tests the code in Octave. The owner runs the whole thing in MATLAB on the demo laptop and tells the planner what happened. Then the planner plans the next packet.
